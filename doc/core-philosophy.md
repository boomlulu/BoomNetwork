# BoomNetwork 核心哲学

> **第一性原理**：玩家按下按钮，角色立刻动。这是不可妥协的体验底线。

---

## 一、基调：自权威，不回滚

BoomNetwork 的网络模型建立在一个核心决策上：

```
每个玩家是自己角色的权威。
自己的操作不是"预测"——它就是事实。
不存在预测错误，因此不需要回滚。
```

这不是偷懒，是第一性原理推导的结果：

1. **回滚解决的是预测错误** — 如果没有预测错误，就不需要回滚
2. **预测错误来自"猜测服务器的裁决"** — 如果我自己就是权威，就不存在猜测
3. **所以：自权威 = 零延迟 + 零回滚**

### 对比

```
传统预测回滚模型：
  按下移动 → 预测执行 → 等服务器确认 → 可能回滚 → 视觉跳变
  复杂度：Event Sourcing + Causal Graph + Snapshot + Resimulate

BoomNetwork 自权威模型：
  按下移动 → 我就是移动了 → 广播给其他人
  复杂度：广播 + 插值
```

## 二、三条公理

整个框架的技术决策从以下三条公理推导：

### 公理 1：自己的操作零延迟

```
我按移动 → 角色立刻动（我是权威，不等任何人）
我按攻击 → 立刻播动画（视觉即时反馈）
```

这一条决定了架构：每个玩家 Own 自己的角色，Owner 对自己的状态拥有绝对权威。不需要服务器确认，不需要预测，不需要回滚。

### 公理 2：别人的状态信任并平滑

```
收到对方的位置 → 直接信任（对方是自己的权威）
网络有延迟     → 用插值/外推平滑展示
```

这一条决定了同步策略：不质疑、不预测对方的状态，只做视觉层面的平滑过渡。对方的 Dead Reckoning 和惯性模型纯粹是视觉层，不涉及逻辑回滚。

### 公理 3：冲突由仲裁者一锤定音

```
A 开枪 → 子弹飞向 B → 谁判定命中？
答案：仲裁者（Host / 专用服务器）

仲裁者说命中 → 就是命中
仲裁者说没中 → 就是没中
双方都不回滚 → 最多有一方的画面做一次视觉修正
```

这一条决定了冲突处理：不在客户端做因果链追踪和回滚。仲裁结果是权威事实，客户端收到后直接应用。

## 三、为什么不做回滚

这是一个经过深思熟虑的取舍，不是遗漏。

### 回滚的代价（我们选择不付的）

| 维度 | 代价 |
|------|------|
| 架构复杂度 | Event Sourcing + Causal DAG + Snapshot + Resimulate — 多出 30-40% 的同步代码 |
| 接入门槛 | 用户必须理解预测、回滚、因果链、快照序列化 — 与框架"5 分钟跑通"的目标矛盾 |
| 调试难度 | Bug 来源从 1 个（逻辑错误）变成 4 个（逻辑/预测/回滚/因果链） |
| 弱网体验 | 150-300ms 延迟下预测窗口 8-18 帧，回滚修正的视觉跳变比输入延迟更令人不适 |
| 维护成本 | 每加一个新功能都要考虑"回滚时怎么办"，永远的隐性税 |

### 不回滚的代价（我们接受的）

| 维度 | 代价 | 缓解手段 |
|------|------|---------|
| 仲裁延迟 | 命中判定需要一个 RTT | 纯视觉预测：立刻播命中特效，等仲裁确认伤害 |
| Host 优势 | 主机客户端仲裁延迟 ≈ 0 | 可选专用服务器仲裁消除优势 |
| 极端竞技公平性 | 格斗/FPS 级别的逐帧公平做不到 | 非目标场景；需要的用户可接入回滚中间件 |

### 覆盖范围

```
自权威 + 仲裁 能做好的：
  ✓ 动作/跑酷/赛车      — 自己操作零延迟，体验完美
  ✓ 派对/休闲/合作      — 冲突少，仲裁延迟不敏感
  ✓ MOBA/射击(非硬核)   — 射击者权威 + 视觉预测，手感够用
  ✓ 建造/经营/沙盒      — 各干各的，几乎不需要仲裁

不在核心目标内的：
  △ 格斗（逐帧判定）    — 需要 GGPO 级回滚，可通过中间件扩展
  △ 硬核 FPS            — 需要精确延迟补偿，可通过服务器端回滚扩展
```

## 四、冲突仲裁策略（可插拔）

仲裁是自权威模型中唯一需要等待的环节。框架提供可插拔的仲裁策略：

| 策略 | 谁判定 | 延迟 | 适用场景 |
|------|--------|------|---------|
| **ShooterAuthority** | 射击者说了算 | 最低（射击者零延迟） | 偏进攻手感的射击游戏 |
| **TargetAuthority** | 受击者说了算 | 中等 | 偏防守体验的动作游戏 |
| **HostAuthority** | 主机客户端判定 | 主机零延迟，其他一个 RTT | 小房间 P2P |
| **ServerAuthority** | 专用服务器判定 | 所有人均等（半个 RTT） | 公平竞技 |

用户根据游戏类型选择策略，框架负责路由仲裁请求和分发结果。

## 六、设计红线

以下是框架开发中不可逾越的约束：

1. **不得在核心层引入回滚** — 回滚只能作为可选中间件存在，框架核心永远不假设回滚的存在
2. **不得要求用户理解预测/回滚** — 用户接入时的心智模型应该是"我操作我的角色，框架帮我同步给别人"
3. **不得牺牲接入简洁性** — 任何新功能如果让 Quickstart 变长，就需要重新评估
4. **零延迟操作不可妥协** — 任何设计如果让自己的操作产生了等待，就是架构方向错了

## 七、一句话总结

> **BoomNetwork 的哲学：你是自己角色的主人，你的操作就是真相。冲突交给仲裁者，不纠结回滚。简单、直接、够用。**
